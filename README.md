# DeskFlow — Migration: MongoDB/Mongoose → PostgreSQL/Prisma

This document covers the full database migration. The frontend (React/Vite) is **unchanged** — it only talks to the REST API, which kept the same contract (`{success, message, data}`, same endpoints). All schema, query, and persistence logic moved from Mongoose to Prisma + PostgreSQL.

---

## 1. Migration Strategy

1. **Model the relational schema** — `User` and `Ticket` become Postgres tables with a real foreign key (`Ticket.createdById → User.id`) instead of a loosely-typed Mongoose `ObjectId` ref.
2. **Replace the ODM** — every `Model.find/create/update` Mongoose call is rewritten to the Prisma Client equivalent (`prisma.model.findMany/create/update`).
3. **Flatten embedded documents** — the `aiAnalysis` sub-document (Mongoose embedded object) becomes flat columns on `tickets` (`ai_summary`, `ai_troubleshooting_steps`, ...), since Postgres has no native embedded-document type.
4. **Move validation/hashing out of the schema** — Mongoose's `pre('save')` hook and instance methods (`comparePassword`, `toSafeObject`) don't exist in Prisma, so hashing and "strip password" logic became explicit application code (`authController.js`, `utils/formatUser.js`).
5. **Swap security middleware** — `express-mongo-sanitize` (a NoSQL-injection guard) is removed since it's MongoDB-specific and meaningless against SQL; Prisma's parameterized queries are the equivalent protection for Postgres.
6. **Re-map error handling** — Mongoose's `err.name`/`err.code` checks are replaced with Prisma's typed `PrismaClientKnownRequestError` codes (`P2002` duplicate, `P2025` not found, `P2003` FK violation).
7. **IDs change shape** — MongoDB `ObjectId` (`_id`) becomes a Postgres `uuid` (`id`). The frontend was updated accordingly (`ticket._id` → `ticket.id`).

No MongoDB code, config, or environment variables remain anywhere in the project.

## 3. Prisma Schema (`prisma/schema.prisma`)

```prisma
model User {
  id        String   @id @default(uuid())
  name      String
  email     String   @unique
  password  String
  role      Role     @default(employee)
  createdAt DateTime @default(now()) @map("created_at")
  updatedAt DateTime @updatedAt @map("updated_at")
  tickets   Ticket[]

  @@index([email])
  @@map("users")
}

model Ticket {
  id          String    @id @default(uuid())
  title       String
  description String
  priority    Priority  @default(Medium)
  status      String    @default("Open")
  category    String    @default("Other")

  aiSummary              String?
  aiTroubleshootingSteps String[]
  aiSuggestedResolution  String?
  aiRecommendedPriority  Priority?
  aiAnalyzedAt           DateTime?

  createdById String @map("created_by_id")
  createdBy   User   @relation(fields: [createdById], references: [id], onDelete: Cascade)

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@index([createdById, createdAt])
  @@index([status, priority])
  @@map("tickets")
}
```

**Design decisions worth calling out:**

- **`Priority` is a real Postgres enum** (`Low`/`Medium`/`High` — no spaces, no ambiguity).
- **`status` and `category` are `String`, not enums.** Prisma enum *values* can't contain spaces, so `"In Progress"` would need a workaround like `InProgress @map("In Progress")` — but then the Prisma Client's JS-level enum key (`InProgress`) would diverge from the string every part of the API and frontend actually uses (`"In Progress"`). Using `String` + application-level validation (already present in `ticketValidation.js`) keeps the API contract byte-for-byte identical to the MongoDB version. A `CHECK` constraint (see `prisma/migrations/.../migration.sql`) enforces the allowed values at the database level too.
- **`onDelete: Cascade`** on the `Ticket → User` relation: deleting a user deletes their tickets, matching the implicit behavior of the old Mongoose setup (orphaned tickets were never cleaned up before — this is actually a correctness improvement).
- **UUID primary keys** (`@default(uuid())`) rather than auto-increment integers, so ids stay non-guessable and don't leak record counts — the closest relational equivalent to Mongo's `ObjectId`.

### ERD

```
┌───────────────────────┐        1        ┌───────────────────────────┐
│         users          │ ─────────────▶ │           tickets           │
├───────────────────────┤        many      ├───────────────────────────┤
│ id (PK, uuid)          │                  │ id (PK, uuid)               │
│ name                    │                  │ title                        │
│ email (UNIQUE, indexed) │                  │ description                  │
│ password                │                  │ priority (enum)              │
│ role (enum)              │                  │ status (string, CHECK)       │
│ created_at               │                  │ category (string, CHECK)     │
│ updated_at               │                  │ ai_summary, ai_*              │
└───────────────────────┘                  │ created_by_id (FK → users.id) │
                                             │ created_at / updated_at       │
                                             └───────────────────────────┘

Indexes: users.email (unique) · tickets(created_by_id, created_at) · tickets(status, priority)
Cascading: ON DELETE CASCADE from users.id → tickets.created_by_id
```

## 5. Mongoose → Prisma: Before/After Reference

**Find one (login lookup)**
```js
// BEFORE
const user = await User.findOne({ email }).select('+password');

// AFTER
const user = await prisma.user.findUnique({ where: { email } });
```

**Find by id**
```js
// BEFORE
const user = await User.findById(decoded.id);

// AFTER
const user = await prisma.user.findUnique({ where: { id: decoded.id } });
```

**Create**
```js
// BEFORE
const ticket = await Ticket.create({ title, description, priority, category, createdBy });

// AFTER
const ticket = await prisma.ticket.create({
  data: { title, description, priority, category, createdById },
});
```

**Find many + populate + sort**
```js
// BEFORE
const tickets = await Ticket.find(filter)
  .populate('createdBy', 'name email')
  .sort({ createdAt: -1 });

// AFTER
const tickets = await prisma.ticket.findMany({
  where: filter,
  include: { createdBy: { select: { id: true, name: true, email: true } } },
  orderBy: { createdAt: 'desc' },
});
```

**Update by id**
```js
// BEFORE
await Ticket.findByIdAndUpdate(id, updates, { new: true });

// AFTER
await prisma.ticket.update({ where: { id }, data: updates });
```

**Text search**
```js
// BEFORE
filter.$text = { $search: search };

// AFTER
where.OR = [
  { title: { contains: search, mode: 'insensitive' } },
  { description: { contains: search, mode: 'insensitive' } },
];
```

## 6. Authentication Refactor

Mongoose let the schema do the work (`pre('save')` hash hook, `comparePassword` instance method, `toSafeObject()`). Prisma models are plain data — there are no hooks or methods — so that logic is now explicit application code:

```js
// src/controllers/authController.js
const user = await prisma.user.findUnique({ where: { email } });
if (!user || !(await bcrypt.compare(password, user.password))) {
  throw new ApiError(401, 'Invalid email or password');
}
const token = generateToken({ id: user.id, role: user.role });
res.json(new ApiResponse(200, 'Login successful', { token, role: user.role, user: formatUser(user) }));
```

`formatUser()` (in `src/utils/formatUser.js`) replaces `user.toSafeObject()` by destructuring off the `password` field before any user object is sent to the client.

## 7. Ticket Controllers (Prisma)

All three endpoints (`POST /api/tickets`, `GET /api/tickets`, `PUT /api/tickets/:id`) keep their exact same route signatures and access-control rules:

- **Employees**: can create tickets, can only list/update their own, **cannot** change `status` (403 if attempted).
- **Admins**: see and update every ticket, including status transitions.

The rules are enforced in `src/services/ticketService.js`, which now uses `prisma.ticket.findUnique` / `update` / `findMany` internally — see the before/after block embedded directly in that file.

## 10. Deployment

### Render (Backend)
1. Root directory: `backend`. Build: `npm install` (runs `prisma generate` via `postinstall`). Start: `node server.js`.
2. **Before first boot**, run `npx prisma migrate deploy` against the production `DATABASE_URL` (Render Shell, or a one-off Job) to create the tables.
3. Environment variables: `DATABASE_URL`, `JWT_SECRET`, `JWT_EXPIRES_IN`, `GROQ_API_KEY`, `GROQ_MODEL`, `CLIENT_URL`, `PORT`, `NODE_ENV=production`.

### Neon / Supabase (Database)
- Create the project, copy the pooled connection string into `DATABASE_URL` (see §4 for the exact format for each).
- Both providers support Prisma's `directUrl` if you want a separate non-pooled connection for migrations — add `directUrl = env("DIRECT_URL")` to the `datasource` block if you hit pooler issues running `migrate deploy`.

- Unchanged from the MongoDB version — `VITE_API_URL` just needs to point at the Render backend URL.

## 11. What Did *Not* Change

- Frontend code (React components, routing, Tailwind styling) — zero changes required, since it only depends on the REST API shape, which was preserved.
- `groqService.js` — the AI integration never touched the database directly, so it's byte-for-byte the same file.
- API response envelope (`{success, message, data}`), route paths, and RBAC rules.
- `.env` variable *names* for JWT/Groq (`DATABASE_URL` replaces `MONGO_URI`, everything else is the same).

## 12. Follow-up Improvements Enabled by Postgres

- Native full-text search via `tsvector` + a GIN index (faster/better-ranked than the current `ILIKE`-based `contains` search) once search volume justifies it.
- Proper relational reporting (e.g. `GROUP BY category, status` for admin analytics) using raw SQL or Prisma's `groupBy`.
- Row-level constraints (the `CHECK` constraints added in this migration) that MongoDB couldn't enforce at the database layer.
- Prisma Studio (`npm run prisma:studio`) for a free local DB admin UI during development.
